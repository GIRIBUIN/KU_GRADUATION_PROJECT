# KUTODO 리팩토링 분석

- 작성일: 2026-08-10
- 분석 범위: `lib/`, `docs/`, `pubspec.yaml`, 정적 분석 결과
- 목적: 기능 변경 전 구조·데이터·유지보수 위험을 파악하고 단계별 리팩토링 기준을 정의한다.
- 제외 범위: 신규 자동 테스트 코드 작성

## 1. 요약

KUTODO는 Repository, Mapper, Service 인터페이스와 Drift 기반 로컬 DB를 이미 사용하고 있어 전면 재작성할 필요는 없다. 현재 가장 큰 문제는 다음 세 가지다.

1. Presentation 계층에 화면, 상태, 업무 흐름, 외부 서비스 조립 책임이 집중되어 있다.
2. 문서·도메인 모델·DB·Repository 구현 사이에 관계와 필드 의미가 일치하지 않는 부분이 있다.
3. Task 생성·수정과 알림, SubTask 저장이 여러 객체에 걸쳐 순차 실행되어 부분 저장 위험이 있다.

생성 코드인 `app_database.g.dart`를 제외하면 프로덕션 코드는 52개 파일, 약 13,220줄이다. `presentation/screens/main/main_shell_screen.dart`는 5,353줄로 전체 프로덕션 코드의 약 40%를 차지한다.

정적 분석 결과 컴파일 오류는 없었으며 deprecated API 사용 1건이 발견됐다.

## 2. 현재 구조의 장점

현재 구조에서 유지할 가치가 있는 요소는 다음과 같다.

- 저장소 계약과 Drift 구현체가 분리되어 있다.
- DB Row와 앱 모델 사이에 Mapper가 존재한다.
- Task와 관계 데이터 저장에 Drift transaction을 일부 사용한다.
- e-campus 연동이 요청, 파싱, 분류, 적용, 흐름 서비스로 나뉘어 있다.
- 생성자 주입을 사용해 주요 의존성을 전달한다.
- DB schema version과 단계별 migration이 존재한다.

리팩토링은 이러한 기반을 없애는 작업이 아니라 책임 경계를 명확하게 만드는 방향으로 진행한다.

## 4. 아키텍처와 모듈화

### 4.1 명목상 레이어와 실제 의존성

현재 디렉터리는 `core`, `data`, `presentation`, `providers`로 구분되어 있지만 실제 `providers`에는 구현이 없다. Presentation은 `data/models`, Repository 계약, Service 계약과 일부 Service 구현체를 직접 참조한다.

Repository 계약도 `data/repositories`에 있어 상위 계층이 Data 계층에 의존하는 형태다. 향후 feature-first 구조로 이동할 경우 Repository 계약은 기능의 domain 또는 application 영역으로 이동하고 Drift 구현체만 data 영역에 두는 편이 자연스럽다.

### 4.2 MainShellScreen 책임 집중

`main_shell_screen.dart`는 다음 책임을 함께 가진다.

- 앱의 하단 탭과 주요 화면 조합
- Task 전체 로딩과 새로고침
- 설정 복구 로직
- Task 완료·삭제·복구·정렬
- 로컬 알림 예약과 취소
- e-campus 로그아웃용 HTTP 객체 생성
- 태그·폴더 CRUD와 트리 정렬
- 홈, 목록, 관리, 설정 UI
- 날짜, D-day, 색상, 정렬, 알림 포맷 유틸

단순히 Widget 클래스만 여러 파일로 옮기면 파일 크기만 줄고 결합도는 그대로 남는다. 화면 분리와 함께 상태 및 사용자 명령을 Controller/Application Service로 이동해야 한다.

### 4.3 외부 서비스 조립 위치

e-campus 동기화 화면은 `http.Client`, Todo Service, Parser, Classifier, Apply Service, Flow Service를 직접 생성한다. 화면은 동기화 상태 표시와 사용자 이동만 담당하고, 객체 조립은 `app.dart` 또는 별도 Composition Root에서 담당하도록 변경한다.

## 5. 데이터베이스 분석

### 5.1 Task–Folder 관계 불일치

문서와 DB는 `TaskFolders` 연결 테이블을 사용해 Task와 Folder를 many-to-many 관계로 정의한다. 그러나 `DriftTaskRepository._replaceRelations()`는 `task.folderIds.take(1)`만 저장한다.

리팩토링 전에 다음 정책 중 하나를 확정해야 한다.

- Task당 폴더 하나: `folderId` nullable FK로 단순화
- Task당 여러 폴더: 현재 연결 테이블을 유지하고 모든 `folderIds` 저장

정책 결정 없이 Repository만 수정하면 현재 UI의 의도와 데이터 모델이 다시 어긋날 수 있다.

### 5.2 사용하지 않는 parentTaskId

`Task.parentTaskId`는 모델과 Tasks 테이블에 존재하지만 현재 SubTask 기능은 별도 `SubTasks.taskId`를 사용한다. 현재 기능에서 계층형 Task를 지원하지 않는다면 다음 migration에서 제거하는 편이 좋다. 향후 계층형 Task를 지원한다면 self-reference FK, 삭제 정책, 순환 참조 방지 규칙을 함께 정의해야 한다.

### 5.3 알림 모델

명세는 Task 하나당 알림 설정 하나를 가정한다. 그러나 `NotificationSettings.taskId`에는 unique 제약이 없다. Repository는 `getSingleOrNull()`을 사용하므로 중복 행이 발생하면 런타임 오류가 날 수 있다.

추가로 다음 필드의 의미를 정리해야 한다.

- `daysBeforeDue`: 실제로는 분 단위이므로 `offsetMinutes`로 변경
- `notifyTime`: 현재 `relative`만 사용한다면 제거하거나 enum으로 제한
- `scheduledAt`: 실제 예약 성공 시각을 저장할지, 계산 값으로만 사용할지 결정

### 5.4 태그–폴더 및 표시 설정

다음 값은 `AppSettings` key-value 테이블의 JSON 문자열로 저장된다.

- `hiddenTagIds`
- `hiddenFolderIds`
- `tagFolderIds`
- `tagSortOrders`

이 구조는 FK를 적용할 수 없어 삭제된 태그와 폴더 ID가 남을 수 있다. 현재 코드에 자동 폴더 관계를 복구하는 로직이 존재하는 것도 저장 구조가 데이터 정합성을 보장하지 못한다는 신호다.

현재 UI가 태그 하나를 하나의 폴더에만 배치한다면 Tags 테이블에 `folderId`, `isHidden`, `sortOrder`를 추가하는 방식이 가장 단순하다. 여러 폴더 배치가 필요하다면 별도 `TagFolders` 관계 테이블을 사용한다.

### 5.5 외래키와 삭제 정책

현재 영구 삭제는 Repository가 TaskTag, TaskFolder, NotificationSetting, SubTask를 순서대로 직접 삭제한다. 이 방식은 모든 삭제가 해당 Repository를 통과할 때만 안전하다.

다음 관계에는 DB 차원의 삭제 정책을 검토한다.

- SubTask → Task
- TaskTag → Task, Tag
- TaskFolder → Task, Folder
- NotificationSetting → Task
- Folder → Parent Folder

가능한 관계는 `ON DELETE CASCADE`를 사용하고, 사용자 확인이나 이동 처리가 필요한 관계는 application 로직에서 명시적으로 처리한다.

### 5.6 조회 성능

Task 목록 조회는 Task를 먼저 조회한 뒤 각 Task마다 Tag 관계와 Folder 관계를 각각 조회한다. Task가 N개이면 기본 조회를 포함해 최대 `1 + 2N`개의 쿼리가 발생한다.

개선 방법은 다음 중 하나다.

- JOIN과 group 처리를 사용한 단일 조회
- Task 목록 조회 후 TaskTag와 TaskFolder를 `IN` 조건으로 각각 한 번씩 조회
- 화면 용도에 맞는 read model 또는 DAO 제공

현재 규모에서는 두 번째 방식이 구현과 유지보수의 균형이 좋다.

### 5.7 권장 인덱스와 제약

DB 정책 확정 후 다음 항목을 검토한다.

- Tasks: `status`, `origin`, `sortOrder`, `dueDate`
- SubTasks: `taskId`
- NotificationSettings: unique `taskId`
- TaskTags: `tagId`
- TaskFolders: `folderId`
- e-campus Task: unique `ecampusSourceKey` 유지
- enum 문자열 컬럼: 허용 값 check constraint 또는 안전한 converter

## 6. 캡슐화와 도메인 규칙

현재 `Task`는 불변 데이터 객체지만 `copyWith`와 상태 전이 메서드가 없다. Repository와 화면이 Task의 모든 필드를 다시 나열해 새 객체를 만든다. 이 구조는 필드 추가 시 수정 범위를 넓히고 상태별 시간 필드를 빠뜨리기 쉽다.

예를 들어 완료 Task를 active 상태로 되돌릴 때 현재 구현은 기존 `completedAt`을 유지한다. 상태와 시간 필드의 불변 조건을 Task 또는 전용 도메인 서비스가 보장해야 한다.

권장 API 예시는 다음과 같다.

```dart
task.copyWith(title: title, dueDate: dueDate);
task.complete(now);
task.reopen(now);
task.markDeleted(now);
task.restore(now);
```

함께 적용할 규칙은 다음과 같다.

- 빈 제목 금지
- `excluded`는 e-campus Task만 허용
- e-campus Task에는 `sourceKey` 필수
- `completed`와 `completedAt` 일치
- `deleted`와 `deletedAt` 일치
- 알림 offset 음수 금지
- Task–Folder 최대 연결 수 정책 준수

## 7. 트랜잭션과 오류 처리

작업 생성 화면은 다음 작업을 순서대로 실행한다.

```text
Task 저장
→ 여러 SubTask 저장
→ NotificationSetting 저장
→ OS 로컬 알림 예약
```

중간 단계에서 실패하면 Task만 생성되거나 일부 SubTask만 생성될 수 있다. 저장 예외가 발생하면 `_isSaving` 상태가 원복되지 않을 가능성도 있다.

권장 구조는 다음과 같다.

1. `TaskDraft`를 application 계층에 전달한다.
2. `TaskAggregateRepository` 또는 전용 DB command가 Task, SubTask, NotificationSetting을 하나의 Drift transaction으로 저장한다.
3. DB commit 후 OS 알림 예약을 실행한다.
4. OS 알림 실패는 DB 저장 실패와 구분해 사용자에게 재시도 가능한 상태로 전달한다.

e-campus 다건 가져오기도 항목별 Repository 호출로 실행된다. 전체 원자성이 필요한지, 성공 항목만 유지하는 부분 성공 정책이 필요한지 명세로 확정해야 한다. 부분 성공을 허용한다면 성공·실패 결과를 명시적인 Result 객체로 반환해야 한다.

## 8. 중복 제거

### 8.1 작업 생성·상세 화면

두 화면에는 다음 구현이 중복된다.

- 제목, 마감일, 우선순위, 알림, 태그, 메모 UI
- 알림 offset picker
- 알림 활성 가능 여부 계산
- 날짜 포맷
- Snackbar 표시
- 태그 생성과 폴더 연결
- SubTask 입력 UI

다음 단위로 추출한다.

- `TaskEditorForm`
- `TaskEditorDraft`
- `TaskEditorController`
- `NotificationOffsetPicker`
- `TaskDateFormatter`
- `TagCreationService`

생성 화면은 새 Draft를 초기화하고, 상세 화면은 기존 Task를 Draft로 변환하는 차이만 유지한다.

### 8.2 색상 처리

hex 색상 정규화, 유효성 검사, Color 변환이 `task_metadata_picker.dart`와 `main_shell_screen.dart`에 각각 존재한다. `core/design_system` 또는 metadata 기능 내부에 `AppColorValue`와 공통 변환 함수를 둔다.

### 8.3 Task 복사

Task 전체 필드를 다시 전달하는 코드가 Repository, 화면, e-campus 적용 서비스에 반복된다. `copyWith`와 도메인 전이 메서드 도입 후 제거한다.

## 9. 상태 관리

현재 상태 관리는 `FutureBuilder`와 `setState` 중심이다. 작은 화면에서는 충분하지만 MainShell처럼 여러 화면과 데이터 소스를 함께 관리하면 전체 Future 교체와 전체 목록 재조회가 반복된다.

상태 관리 패키지 도입 자체를 목표로 삼지 않는다. 우선 다음처럼 화면별 Controller를 분리한다.

- `MainShellController`: 탭과 앱 수준 세션 상태
- `HomeController`: 홈용 Task 요약과 태그 필터
- `TaskListController`: 목록, 정렬, 필터, 순서
- `MetadataController`: 태그·폴더 트리와 표시 상태
- `SettingsController`: 앱 설정
- `TaskEditorController`: 생성·수정 Draft와 저장 상태
- `EcampusSyncController`: 로그인·수집·비교·적용 상태

초기에는 Flutter 기본 `ChangeNotifier` 또는 `ValueNotifier`로도 충분하다. 상태 흐름이 복잡해진 뒤 Riverpod 같은 패키지 도입 여부를 판단한다.

## 11. 적용할 디자인 패턴

패턴 적용 자체가 목적이 되어서는 안 된다. 현재 문제에 필요한 패턴만 사용한다.

| 패턴 | 적용 위치 | 목적 |
| --- | --- | --- |
| Repository | 기존 구조 유지 및 계약 위치 조정 | 저장 방식 격리 |
| Mapper | 기존 구조 유지 | DB Row와 도메인 모델 분리 |
| Application Service | Task 명령, metadata 관리, 동기화 | 여러 Repository 흐름 조합 |
| Controller/ViewModel | 화면별 상태 | UI와 상태·업무 명령 분리 |
| Composition Root | `app.dart` 주변 | 객체 생성과 연결 집중 |
| Aggregate Repository/Unit of Work | Task 묶음 저장 | DB 원자성 확보 |
| Strategy | 정렬·필터가 확장될 때 | 조건문 증가 통제 |

## 12. 공통 코딩 양식

다음 규칙을 프로젝트 공통 기준으로 정의한다.

- 공개 Widget 또는 주요 클래스는 가능한 한 파일 하나에 하나씩 둔다.
- 화면 파일은 shell과 조합 역할에 집중하고 업무 로직을 직접 구현하지 않는다.
- 화면에 Repository가 여러 개 전달되기 시작하면 Controller 또는 Service 경계 도입을 검토한다.
- ID 생성은 `microsecondsSinceEpoch` 문자열 조합 대신 중앙 `IdGenerator`를 사용한다.
- 시간 생성은 주입 가능한 `Clock` 또는 `DateTime Function()`을 사용한다.
- 알림 시간 단위는 이름에 명시한다.
- enum 문자열과 DB 컬럼 이름을 일관되게 관리한다.
- import 방식은 package import 또는 정해진 상대 import 방식 하나로 통일한다.
- `dart format`과 `flutter analyze --no-pub`를 변경 완료 기준에 포함한다.
- deprecated API 경고를 방치하지 않는다.
- README의 예정 구조와 실제 구현이 달라지면 같은 변경에서 문서를 갱신한다.

## 13. 단계별 리팩토링 계획

### 0단계: 정책 결정

- Task–Folder 관계를 1:N 또는 N:M 중 하나로 확정
- `parentTaskId` 유지 여부 결정
- 태그–폴더 관계의 cardinality 결정
- 알림 필드와 예약 실패 정책 결정
- e-campus 다건 적용의 전체 성공 또는 부분 성공 정책 결정

### 1단계: 동작 변경 없는 파일 분리

- MainShell에서 Home, TaskList, Management, Settings 화면 분리
- 공통 Widget과 순수 포맷 함수 이동
- 미사용 `SettingsScreen`, debug 화면 처리 결정
- 문서와 실제 구조 동기화

### 2단계: UI 책임 분리

- 작업 생성·상세 공통 `TaskEditorForm` 도입
- 화면별 Controller 도입
- HTTP 및 Service 조립을 Composition Root로 이동
- 화면이 직접 수행하는 설정 복구·태그 생성 로직 이동

### 3단계: 도메인 캡슐화

- Task `copyWith` 도입
- 상태 전이 메서드와 불변 조건 정의
- 중앙 ID 생성기와 Clock 도입
- 오류 타입과 사용자 메시지 매핑 분리

### 4단계: DB v6 정리

- 확정한 Task–Folder 정책 반영
- 사용하지 않는 필드 제거 또는 FK 보강
- NotificationSetting의 unique Task 제약 추가
- 태그·폴더 표시 관계를 설정 JSON에서 정규 테이블/컬럼으로 migration
- cascade 정책과 인덱스 추가
- Task 관계 조회의 N+1 제거

### 5단계: 기능 단위 모듈화

- tasks, metadata, notifications, ecampus_sync, settings로 이동
- Repository 계약과 구현체 위치 구분
- 기능별 공개 API 외 내부 클래스 캡슐화
- 오래된 README와 중복 문서 정리

## 14. 테스트 코드 없이 검증하는 방식

신규 테스트 코드 작성은 이번 리팩토링 범위에서 제외한다. 대신 변경 위험을 통제하기 위해 다음 절차를 사용한다.

- 한 번에 하나의 책임 또는 모듈만 변경한다.
- 구조 변경과 기능 변경을 같은 단계에서 섞지 않는다.
- DB migration과 UI 변경을 분리한다.
- 각 단계에서 `dart format`을 확인한다.
- 각 단계에서 `flutter analyze --no-pub`를 실행한다.
- Android debug build를 확인한다.
- DB 변경 전 기존 앱 데이터 백업 또는 개발용 DB 복사본을 준비한다.
- 수동 회귀 체크리스트로 핵심 흐름을 확인한다.

수동 확인 대상은 다음과 같다.

- 신규 설치 및 기존 DB upgrade
- Task 생성·수정·완료·미완료·삭제·복구·영구 삭제
- SubTask 생성·완료·삭제
- 태그·폴더 생성·수정·정렬·이동·삭제
- e-campus 로그인·동기화·제외·다시 가져오기
- 앱 재시작 후 데이터 유지
- 알림 설정·예약·취소
- 빈 데이터, 네트워크 오류, 세션 만료 화면

## 15. 최종 권고

첫 구현 작업은 DB migration이 아니라 `main_shell_screen.dart`의 기계적 화면 분리로 시작하는 것이 안전하다. 단, 분리 전에 0단계의 데이터 정책을 문서로 확정해야 이후 Controller와 DB API를 다시 설계하는 일을 줄일 수 있다.

권장 실행 순서는 다음과 같다.

```text
정책 확정
→ MainShell 파일 분리
→ TaskEditor 공통화
→ Controller/Application Service 도입
→ 도메인 상태 전이 캡슐화
→ DB v6 migration 및 조회 최적화
→ feature-first 모듈 이동
→ 문서·dead code 정리
```
