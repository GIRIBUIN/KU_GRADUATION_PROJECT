# 개선 작업 기록

최신 상태(2026-10-31): UI-006~UI-016 후속 코드는 기능별 11개 커밋으로 분리·push했고, 관련 증거와 작업 기록은 별도 문서 커밋으로 정리한다. 아래 ‘커밋 미수행’은 각 작업 당시 상태다. [커밋 정리](커밋%20정리%202026-10-31.md), [최종 검증 요약](evidence/commits/ui-final-verification-20261031.json)을 현재 기준으로 본다. Android 설치·실제 계정 로그인 검증은 남아 있다.

## 방향 — 2026-10-29

- Flutter로 진행. Android·iOS를 먼저 지원하고 이후 웹으로 확장한다.
- Kotlin 개발본은 DB·동기화 로직을 참고하는 용도로 보존한다.
- 순서: 변경 전 측정 → DB 개선 → 같은 조건으로 재측정 → 기존 UI 연결 → 기기 간 동기화.
- UI는 기존 화면을 우선 연결한다. 디자인 정리는 이후에 진행한다.
- 기기 간 동기화는 같은 사용자의 여러 기기에서 앱 데이터를 맞추는 기능이다. 기존 eCampus 일정 가져오기와 별개다.
- DB 개선 시 기기 간 데이터 식별과 삭제 전달을 고려한다. 계정·서버·충돌 처리 정책은 동기화 구현 전에 결정한다.

## DB-001 — 일정 목록 조회 기준 측정

- 대상: `DriftTaskRepository.getTasks()`의 기본 active 목록 조회.
- 이유: 목록을 읽은 뒤 일정마다 태그와 폴더를 추가 조회한다. DB 개선 전 비용을 확인한다.
- 변경: 수동 실행용 측정 코드와 JSON 결과만 추가. 앱 코드·스키마·사용자 DB는 변경하지 않았다.
- 기준 코드: `7fabd858d7d3acee03360e8e03d5186fa80326b3`. 관련 파일의 해시는 JSON에 별도 저장했다.
- 환경: Windows 11, Flutter 3.44.7, Dart 3.12.2, SQLite 3.53.0, 메모리 DB.
- 입력: 합성 active 개인 일정 100/1,000개, 일정당 태그 2개·폴더 1개, 고정 시각.
- 방법: 크기별 예열 3회 후 10회 측정. DB 생성·입력·결과 검사는 시간에서 제외한다. SELECT 횟수 계측 비용은 포함한다.

| 일정 수 | 조회 시간 중앙값 | p95       | 조회당 SELECT 수 |
| ------- | ----------------:| ---------:| ----------------:|
| 100개   | 16.204 ms        | 22.897 ms | 201회            |
| 1,000개 | 96.2755 ms       | 99.344 ms | 2,001회          |

선택한 기준 결과: [측정 원본](evidence/db/task-list-2026-10-29T14-17-14-061288Z.json).
최초 시험 실행 결과도 같은 디렉터리에 보존했다. 위 표는 측정 코드 포맷 정리 후 재실행한 값이다.
10회 표본의 p95는 nearest-rank 방식으로 계산해 최댓값과 같다.

**해석:** 현재 입력에서는 SELECT 수가 `1 + 일정 수 × 2`로 늘어났다. 목록의 관계 데이터 일괄 조회를 첫 성능 개선 후보로 삼을 수 있다. 아직 개선 전이므로 개선 효과는 주장하지 않는다.

**한계:** PC에서 실행한 예열된 메모리 DB 기준이다. 모바일 실기기·디스크·UI·네트워크 성능이나 전체 앱의 병목을 입증하지 않는다.

측정 코드: [task_repository_benchmark.dart](../test/benchmarks/task_repository_benchmark.dart).
기본 테스트 실행에는 포함되지 않는다. 직접 실행하면 시각이 붙은 새 JSON이 생성된다.

```powershell
C:\flutter\bin\flutter.bat test --no-pub --reporter expanded test/benchmarks/task_repository_benchmark.dart
```

이번 확인은 측정 1건과 기존 Task 저장소 테스트 8건, 총 9건 통과했다. 실제 실행 명령:


## DB-002 — Kotlin·Flutter 비교와 기존 로직 재현

- Kotlin의 원본/일정 분리와 prepare/review/commit 구조를 기준으로 Flutter의 실제 사용 기능을 비교했다.
- [DB 재설계 비교와 적용안](specifications/DB%20재설계%20비교와%20적용안.md)에 보존 항목·데이터 모델·변경할 처리 규칙을 정리했다. 앱 DB는 아직 교체하지 않았다.
- 임시 메모리 DB에서 폴더 관계 축소, 완료 해제 후 시각 잔존, 메모 덮어쓰기, 예상 밖 HTML의 빈 응답 처리와 preview 저장, 부모 삭제 후 자식 참조 잔존을 재현했다.
- [재현 원본](evidence/db/contract-audit-2026-10-29T14-39-52-139024Z.json)에 입력·관찰값·코드 해시·실행 환경을 저장했다. 실제 기기·HTTP·Kotlin 전체 실행 결과는 아니다.
- 직접 재현: `flutter test --no-pub --reporter expanded test/benchmarks/db_contract_audit.dart`.
- 사용자 확인: 폴더는 한 단계, 태그는 전역 독립 분류로 둔다. 전체 목록에서 태그 조회와 특정 폴더 안에서 태그 조회를 모두 지원한다. Tag.folderId는 두지 않는다. 기존 하위 폴더의 ID·일정 연결·원래 경로는 이관 때 보존하며, 옛 태그 배치는 이관 기록으로만 남긴다.

## DB-003 — OCR 가져오기를 고려한 입력 구조 변경

- 사용자 제안: eCampus 앱 화면을 사용자가 직접 이동·스크롤하고 OCR로 수집한 뒤 검토해서 추가한다. WebView 연동 가능 여부는 확정하지 않았다.
- [OCR 가져오기와 DB 변경](specifications/OCR%20가져오기와%20DB%20변경.md)에 기술 검토·중복 후보 처리·측정 계획을 기록했다. 공식 문서를 확인했으며 실제 캡처·OCR 구현이나 측정은 아직 하지 않았다.
- DB 기준안에 ImportSession·ImportObservation을 추가하고 외부 원본 ID를 선택값으로 바꿨다. 내부 항목은 UUID로 식별하고 OCR 문자열 해시는 후보 비교에만 사용한다.
- 화면에서 보이지 않는 항목은 기존 일정에 영향을 주지 않는다. 부분 수집을 전체 동기화로 취급하지 않는다.
- Android 실시간 화면 수집과 iOS 수집 UX는 별도 검증한다. 공통 첫 검증은 스크린샷 OCR로 진행할 수 있다. 앱 코드와 기존 DB는 변경하지 않았다.

## DB-004 — 포트폴리오 우선 범위 검토

- 사용자 고민: 배포 없이 WebView 기반으로 개발 단계 포트폴리오를 먼저 완성하고, OCR은 여유가 있을 때 진행할 수 있는지 검토 중이다. 최종 확정된 결정으로 기록하지 않는다.
- 권장안: DB·로직 개선 → WebView 수동 가져오기·기존 UI 연결 → 전후 측정·오류 재현 → 기기 간 동기화 → 시연과 포트폴리오 정리. OCR은 후속 과제로 둔다.
- DB 기준안에서 OCR 구현을 선행 조건으로 제거했다. 원본·일정 분리와 내부 UUID를 유지해 입력 경로를 교체할 수 있게 하고, OCR 전용 관측·캡처 테이블은 지금 구현하지 않는 안이다.
- 비배포 여부와 학교가 허용한 연동 범위는 별개로 구분한다. 실제 계정 연동이 제한되면 익명화 HTML fixture 기반 검증을 실제 연동 성공과 구분해 기록한다.
- 2026-10-30 사용자 확인: 일단 WebView를 고려하는 방향으로 진행한다. 현황 확인 결과 실제 앱 DB는 여전히 schemaVersion=5이며, 지금까지 변경한 것은 비교·설계 문서와 측정·재현 코드다. 새 스키마·마이그레이션·앱 연결은 아직 구현하지 않았다.

## DB-005 — Flutter DB 버전 6 적용 (2026-10-30)

- 일정과 eCampus 원본을 분리하고, 단일 폴더·전역 태그·완료/삭제 시각·하위 일정 순서를 DB에 적용했다. 기존 화면 DTO는 호환 경계로 유지한다.
- v5 원본 테이블은 legacy_v5_*로 그대로 보존한다. ID·메모·관계·순서를 이관하고 하위 폴더는 경로를 표시한 독립 폴더로 펼친다. 복수 폴더·고아 참조·중복 알림·분해 불가 원본키는 migration_issues에 기록한다. 모순된 연결을 임의로 첫 값만 선택하지 않는다.
- 외래키를 연결마다 활성화했다. 알림 규칙은 분 단위·일정당 1개로 제한하고 기기별 예약 상태와 분리했다. 기기 알림 ID 충돌도 별도로 처리한다.
- 미리보기는 기존 일정을 변경하지 않는다. 제목·마감일을 각각 선택해 적용하며 사용자 메모·태그·폴더는 보존한다. 새 항목의 분류는 사용자가 지정한다. 선택된 여러 항목 반영과 일반 일정/하위 일정/알림 규칙 저장을 각각 트랜잭션으로 묶었다.
- 가져오기를 반복해도 같은 외부 식별키로 중복 추가하지 않는다. 미리보기 뒤 사용자가 수정한 일정은 재확인하도록 막는다. 완료 해제는 완료 시각을 지우고 휴지통 복원은 이전 완료 여부를 유지한다.
- Android 오늘 위젯 SQL을 새 구조에 맞췄고, 업데이트 직후 아직 v5인 DB에서도 완료 처리가 되도록 분기했다. OS 알림·위젯 갱신은 DB 저장 후 수행한다.

같은 입력의 조회 비교: 크기별 예열 3회, 측정 10회. PC·메모리 DB·동일한 합성 일정과 태그/폴더 조건이다.

| 일정 수 | 변경 전 중앙값 | 변경 후 중앙값 | 변경 전 SELECT | 변경 후 SELECT |
| --- | ---: | ---: | ---: | ---: |
| 100개 | 16.204 ms | 4.3145 ms | 201 | 3 |
| 1,000개 | 96.2755 ms | 20.5745 ms | 2,001 | 5 |

- [변경 전 원본](evidence/db/task-list-2026-10-29T14-17-14-061288Z.json) / [변경 후 단독 측정 원본](evidence/db/task-list-2026-10-29T15-37-43-034316Z.json). 1,000개 중앙값은 약 78.6% 감소했다. 모바일·디스크·UI 성능 수치로 해석하지 않는다.

[검증 요약·소스 해시·APK 해시](evidence/db/validation-summary-v6-20261030.json), [테스트 원본](evidence/db/validation-v6-final-20261030.jsonl), [정적 분석](evidence/db/analyze-v6-20261030.txt), [빌드 원본](evidence/db/build-v6-final-20261030.txt).

- 실제 사용자 DB와 로그인 계정은 사용하지 않았다. iOS 빌드·실행, 실제 eCampus 연동, 실기기 위젯·알림 확인, 기기 간 동기화와 OCR은 미수행이다. 단일 로컬 데이터셋만 지원하며 다중 계정·클라우드 계정 범위는 후속 설계다.

## DB-007 — DB 관계도와 Git 정리 (2026-10-30)

- 실제 v6 Drift 코드의 13개 테이블과 외래키 9개를 [DB 관계도](diagrams/db-v6.md)와 [변환용 Mermaid 원본](diagrams/db-v6.mmd)으로 저장했다. 화면 DTO·이관 백업 테이블은 운영 스키마와 구분했다.
- [증거 자료 안내](evidence/db/README.md)에 선택한 전후 측정, 로직 재현, 최종 테스트·분석·빌드·설치 원본을 연결했다. 이전 단계의 기록을 이후 결과로 덮어쓰지 않았다.

## DB-010 — 상위 폴더·목록·수집함 적용 (2026-10-30)

- 목록 보관·복원은 Task 소속을 바꾸지 않는다. 상위 폴더 삭제는 목록만 폴더 밖으로 이동한다. 완료·휴지통 Task의 원래 목록 정보도 유지한다.
- 신규 eCampus 가져오기는 기본적으로 eCampus 폴더의 강의별 목록에 배치한다. 강의 식별값으로 연결하며 기존 Task의 수동 이동을 보존한다. 가져오기에서 수집함·다른 목록을 직접 지정할 수도 있다.
