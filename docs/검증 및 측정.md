# KUTODO 검증 및 측정

현재 기능 설명과 과거 실행 결과를 분리한다. 이 문서는 **기존 측정·검증 기록의 요약**이며 이번 문서 정리에서 재측정한 값이 아니다.

## DB v5 → v6 → v7 개선 과정

발표에서는 버전 번호만 나열하기보다 각 단계의 문제, 판단, 변경, 검증을 연결한다.
v5→v6는 조회 성능·데이터 처리 규칙 개선, v6→v7은 분류 요구사항 변경과 안전한 데이터 이관 경험이다.
모든 변경의 효과를 조회 속도 하나로 설명하지 않는다.

| 단계 | 발견한 문제·요구 | 변경과 판단 | 남아 있는 검증 |
| --- | --- | --- | --- |
| v5 기준 확인 | 목록 조회 뒤 Task마다 관계 데이터를 추가 조회. 사용자 일정과 eCampus 원본 정보 혼재 | 변경 전 시간을 측정하고 SELECT 수를 계측. 고정 입력으로 기존 로직 오류 재현 | 100개 201회, 1,000개 2,001회 SELECT. 메모·완료 시각·preview 부작용 등 재현 원본 |
| v5→v6 | 데이터가 늘수록 추가 조회 증가. 원본 갱신과 사용자 편집의 경계, 저장 원자성·관계 제약 보완 필요 | 관계 데이터 일괄 조회. Task·원본 분리, 필드별 반영, 읽기 전용 preview, transaction·FK·이관 기록 적용 | 동일 조건 전후 측정, 오류 수정 전후 재현, v6 적용 당시 테스트 125건 |
| v6→v7 | 폴더 하나가 Task 저장 위치와 목록 그룹 역할을 함께 담당. 모든 Task가 목록 하나에 소속되어야 한다는 요구 | 폴더→목록→할 일로 분리. 필수 list_id와 기본 미지정 목록 도입, 기존 소속·완료·휴지통 연결 보존 | 필수 소속·과목 배치·이관·실패 rollback 검증. 도입 당시 전체 테스트 186건. v6 대비 성능 측정은 아직 없음 |

### 사례 1. 조회 병목을 발견하고 v6에서 개선

- **발견:** 할 일 100개와 1,000개에서 SELECT가 각각 201회·2,001회였다. Task별 관계 조회로 `1 + 2 × Task 수`만큼 증가했다.
- **판단:** SQL 한 번의 실행 시간뿐 아니라 호출 횟수 증가를 개선 대상으로 삼았다.
- **변경:** Task를 먼저 읽고 관계 데이터를 ID 묶음으로 일괄 조회했다. 500개 단위로 나누므로 이 입력에서는 100개 3회, 1,000개 5회다. 데이터 크기와 무관한 고정 3회라고 설명하지 않는다.
- **검증:** 같은 합성 데이터·환경·계측 범위에서 다시 측정했다. 1,000개 중앙값 96.2755→20.5745ms, 약 78.6% 감소다. 상세 수치와 한계는 아래 표를 따른다.

### 사례 2. 데이터 처리 오류를 재현하고 v6에서 보완

| 고정 입력에서 재현한 문제 | 수정 후 확인한 동작 |
| --- | --- |
| 폴더 A·B를 입력했는데 A만 저장 | 당시 단일 소속 계약에 맞지 않는 입력은 부분 저장 없이 거부 |
| 완료를 해제해도 completedAt 잔존 | 미완료로 돌아오면 완료 시각 제거 |
| eCampus 변경 반영으로 사용자 메모 덮어쓰기 | 원본 변경 이후에도 사용자 메모 보존 |
| 예상 밖 HTML을 정상 빈 목록으로 보고 preview에서 기존 일정 완료 | 파싱 오류를 보고하고 preview 전후 기존 상태 유지 |
| FK 비활성 및 부모 삭제 후 참조 잔존 | 연결의 FK 활성화와 당시 폴더 삭제·연결 해제의 원자성 확인 |

[수정 전 재현](evidence/db/contract-audit-2026-10-29T14-39-52-139024Z.json)과 [수정 후 재현](evidence/db/contract-audit-2026-10-29T15-36-30-841250Z.json)은 합성 메모리 DB/API 경계의 결과다. 실제 로그인·네트워크·사용자 DB 결과로 확대하지 않는다.
단일 폴더 소속은 v6 당시 계약이며, 현재 v7의 필수 목록 소속과 구분한다.

### 사례 3. 분류 요구를 v7로 옮기면서 기존 데이터 보존

- **문제:** `학교`로 과목별 목록을 묶되 Task는 과목 목록에 들어가야 한다. v6에는 목록을 묶는 별도 상위 폴더가 없었다.
- **변경:** `folder_groups`는 목록을 묶고 `task_lists`는 Task의 저장 위치가 된다. 태그는 폴더·목록과 독립적으로 Task에 연결한다.
- **이관:** 기존 v6 폴더를 같은 ID의 목록으로 옮기고 미분류 Task는 미지정에 배치한다. 완료·휴지통·원본·하위 항목 연결과 기존 행 백업을 보존한다.
- **검증:** 필수 목록, 잘못된 소속 거부, 폴더 삭제 후 목록 유지, 과목별 기본 배치와 수동 이동 보존, 이관 시 외래키·실패 rollback을 확인했다. [당시 검증과 원본](evidence/db-v7/README.md), [v6→v7 이관 코드](../lib/data/local/schema_v7_migration.dart).
- **효과의 범위:** 분류 규칙과 이관 안전성을 검증했다. v7이 v6보다 빠르다는 측정 결과는 아직 없다. 도입 당시 보관 UI와 현재 숨김 UI의 차이는 현재 명세를 따른다.

### 다음에 직접 재현할 범위

1. v5 기준 측정과 재현 결과를 읽고 Task 수에 따라 SELECT가 증가한 경로를 설명한다. [v5 측정·재현 코드 보관본](evidence/db/baseline-harness-v5.zip)과 각 JSON의 소스 해시가 기준이다. 현재 앱 DB를 과거 버전으로 되돌리지 않는다.
2. v6의 일괄 조회가 무엇을 줄였는지, 기존 데이터·사용자 편집을 어떻게 보존했는지 수정 전후 코드와 결과를 대조한다.
3. v7에도 같은 입력·조회 조건의 측정을 추가해 세 버전의 결과를 비교한다. 실행 환경이 달라지면 비교할 과거 버전도 같은 환경에서 다시 측정하고, 새 결과는 별도 파일로 남긴다. 아직 이 재측정은 수행하지 않았다.

설명 순서는 **문제 발견 → 기준 측정·재현 → 개선 선택 → 데이터 이관 → 전후 검증 → 남은 한계**로 잡는다.

## DB 목록 조회 개선

v5→v6 도입 당시 같은 Windows 환경의 예열된 Drift 메모리 SQLite와 합성 데이터에서 측정했다.
할 일당 태그 2개·소속 1개, 크기별 예열 3회 후 10회 반복이다. 조회와 관계 데이터 변환·SELECT 계측은 포함하고 DB 생성/입력/결과 검사는 제외했다.

| 할 일 수 | 변경 전 중앙값 | 변경 후 중앙값 | 조회당 SELECT |
| --- | ---: | ---: | ---: |
| 100 | 16.204 ms | 4.3145 ms | 201 → 3 |
| 1,000 | 96.2755 ms | 20.5745 ms | 2,001 → 5 |

원본: [변경 전](evidence/db/task-list-2026-10-29T14-17-14-061288Z.json), [변경 후 단독 실행](evidence/db/task-list-2026-10-29T15-37-43-034316Z.json).
각 반복 값·환경·소스 해시·타이머 범위를 보존했다. Task 관계의 개별 추가 조회를 일괄 조회로 줄인 결과다.
이 수치를 현재 v7·서브 작업 UI·디스크 DB·Android 전체 앱 성능이나 사용자 편의성 향상으로 확대 해석하지 않는다.

## 실제 기기와 한계

Galaxy S24 설치·MainActivity 실행 및 APK 해시는 최신 서브 작업 요약에 기록돼 있다.
과거 10월 실기기 검증은 [당시 미팅 기록](history/미팅%20검증%202026-10-14.md)의 범위에서만 해석한다.
최근 설치 성공을 새 WebView 계정 로그인·모든 위젯 탭·자정/절전·OS 알림의 실제 조작 완료로 쓰지 않는다.
iOS·웹·기기 간 동기화·OCR·사용자 평가는 완료 증거가 없다.

## 포트폴리오·보고서에 남길 방식

문제 → 수정 이유·범위 → 재현 조건 → 결과 → 한계 순서로 짧게 연결한다.
실행 날짜·소스 commit/해시·명령·기기/OS·입력 크기·원본 결과를 함께 남긴다.
개인 일정·계정·쿠키·세션·원본 HTML·기기 DB는 공개 증거에 넣지 않는다.
새 측정은 별도 파일로 추가하고 예전 JSON·로그·캡처·기준 harness를 현재 값으로 덮어쓰지 않는다.
